Capability 1: Reusable PIDs (codex's unified_exec)

Functional summary

Codex exposes a process manager that holds up to 64 PTY-backed processes simultaneously, keyed by integer process_id. The model-facing tool surface has three operations:

  • exec_command(command, cwd, ...) — spawn a new PTY-backed process; returns a process_id and an initial output chunk.
  • write_stdin(process_id, input, yield_time_ms, max_output_tokens) — write to an existing process's stdin and poll for new output. input="" is a pure poll.
  • (implicit) terminate-all on session close.

Output is held in a 1 MiB head-tail ring buffer per process so the model can poll without losing the prologue. Yield times clamp 250ms–30s; default background idle is 5 min. Approval/sandbox runs once on first spawn and is cached so reuse doesn't re-prompt.

Concrete behavioral gaps Rohan noticed

  • Cannot run a Python REPL / pdb / ipython interactively across calls. Each "check" reloads imports and state.
  • Cannot run npm run dev / file watchers / live servers and react to streaming output — the 2-min timeout kills them.
  • Cannot keep a psql / redis-cli / SSH session open across tool calls.
  • State (loaded models, DB connections, env mutations) cannot persist between tool calls without writing to disk.

Capability 2: Interactive subagents (codex's AgentControl)

Functional summary

Codex has a real multi-agent system. An AgentControl object is shared across a tree of agents rooted in a top-level session. The model-facing tool surface (multi-agent v2) is a set of tools exposed as functions:

  • spawn — create a sibling subagent with role/initial-operation; runs concurrently with siblings.
  • send_message — deliver a message to a named sibling or to the parent (mailbox-backed).
  • followup_task — queue a continuation for an existing subagent.
  • wait — block on a subagent's completion or on an inbound mailbox message.
  • list_agents — introspect siblings and their state.
  • close_agent — terminate a subagent.
  • message_tool — (v2) message-passing variant.

Subagents are full sibling Sessions running on the same Tokio runtime, sharing the AgentControl. Each has its own conversation history and turn loop. Cross-agent messages flow through a shared Mailbox. Lifecycle events (CollabAgentSpawnBegin/End, CollabAgentInteractionBegin/End, CollabWaitingBegin/End, CollabCloseBegin/End, CollabResumeBegin/End) are emitted to the parent's event stream.

There are two generations of the protocol: multi_agents (v1) and multi_agents_v2, gated by the MultiAgentV2 feature flag. v2 is the newer/active path; v1 still exists.

Concrete behavioral gaps Rohan noticed

  • Subagents currently run sequentially — N subagents take ~N× the wall time of one.
  • Subagents run in isolation — cannot send each other messages mid-work to coordinate.
  • Subagents return only a single final string to the parent — no streaming, no intermediate signals.
  • The main agent has to absorb every subagent's full transcript-summary into its own context to do correlation work; this both bloats main-agent context and offloads coordination to it.
  • Patterns like "debate two agents", "split-and-conquer over a monorepo with cross-talk", or "observer + worker" are not natively expressible.
