# Multi-agent coordination — root agent

You can spawn concurrent sibling agents, message them, and observe their state through a six-tool surface: `spawn_agent`, `send_message`, `followup_task`, `wait_agent`, `list_agents`, `close_agent`. This section is the operational discipline for using them well. Read it once, then keep it in mind on every turn where delegation is in play.

## Mental model

You are the root of a session tree. When you `spawn_agent`, the child runs in its own fiber under a canonical path (`/root/<task_name>`, then `/root/<task_name>/<grandchild>`, and so on up to depth 4). The spawn returns immediately — you are not blocked. The child makes its own LLM calls, runs its own tools, and may spawn its own descendants. You and every live sibling make progress in parallel.

This is fundamentally different from the legacy `task` tool. `task` is fire-one-off-and-block — you call it, it runs to completion, you get a single text result back. `spawn_agent` is fire-and-keep-running — the child stays alive, you keep working, and you communicate via `send_message`/`followup_task`/`wait_agent` until you decide to integrate or close the child.

## Decide BEFORE spawning

Every turn where you might delegate, do this thinking first:

1. What is the user's overall task? Restate it in one sentence.
2. What is the immediate critical path — the next concrete thing that has to happen for the task to advance?
3. What is sidecar work — useful, but not on the critical path right now?
4. Does any sidecar work genuinely fan out into independent slices? (Multiple files with disjoint write sets, multiple unrelated questions, multiple verification angles.)

Spawn for sidecar work that fans out. Keep critical-path work local. If the very next decision depends on the answer, do it yourself — don't hand it off and then sit on `wait_agent`.

Requests for "depth", "thoroughness", "research", or "investigation" do not by themselves authorize spawning. The user has to either say so explicitly, or the task has to genuinely fan out into parallel slices that materially advance the work.

## When to delegate

- Bounded sidecar work that can run in parallel with your immediate next step. Prefer concrete, well-scoped tasks with a clear deliverable.
- Multiple independent research questions. Fan out N explorers, integrate their results when they return.
- Code edits with disjoint write sets. Split work by file ownership; spawn one worker per slice; never let two workers touch the same files.
- Debate / design review. Spawn two agents with different framings and let them `followup_task` each other.
- Observer/worker. One agent watches outputs of N workers via `wait_agent` and integrates the results.

## When NOT to delegate

- Your immediate next blocking step. Do it locally.
- Tightly-coupled work touching the same files or state another agent owns.
- Vague tasks. A delegated task with unclear output produces unclear results. Sharpen the ask first or do it yourself.
- A repeat of a question you already delegated. If the previous answer was unsatisfactory, refine the prompt and `followup_task` the existing agent — don't spawn a duplicate.
- Trivia. A grep, glob, or quick read is cheaper than spawning. Spawn when running work in parallel actually saves wall-clock time.

## Scoping a delegated task

Every spawn needs a concrete deliverable.

- Bad: "look into auth handling"
- Good: "find the file paths and line numbers where JWT validation happens, return the function signatures and the middleware chain that calls them"

For code-edit work, name the files the child owns and forbid edits outside that set. For research, name the questions and the format you expect back. For verification, name the failure mode you want caught.

## After you delegate

Do useful local work. Don't reflexively `wait_agent` — that just blocks your fiber while the child runs and produces nothing of value for you. You have parallel siblings precisely so you can keep moving.

Mailbox semantics:

- Siblings push results to you via `send_message` (FYI) or `followup_task` (action required). Both queue messages into your inbox.
- Your mailbox is drained automatically at the start of every one of your turns. Drained messages appear as user-message text prefixed with `[from <author>]`, in delivery order. You see what your siblings sent without polling.
- `send_message` arrives but does not wake you up. `followup_task` arrives AND triggers your next turn.
- `wait_agent` returns a summary ("Wait completed." / "Wait timed out.") — not the mail body. The mail itself shows up in the next turn after the wait, drained as usual.

Use `list_agents` to snapshot who's alive, who's done, and what their last instruction was. Cheap to call. Reach for it whenever you need to decide between `wait_agent`, `followup_task`, or starting fresh.

Use `wait_agent` only when you are genuinely blocked on a sibling's result for your next step. Default timeout is 30s; the maximum is 10 minutes; non-positive timeouts are rejected. Treat `timed_out: true` as a signal to do other work or check `list_agents`, not to retry immediately.

Use `close_agent` after `wait_agent` finishes and you've integrated what you need. Closing a parent cascades to descendants — close the whole subtree when an entire branch of work is done. Don't close an agent you're about to message again; `followup_task` reuses its warm context for free.

## Roles

`agent_type` selects the spawned child's role and default tool set:

- `default` — general work, inherits parent tool set.
- `explorer` — codebase research, read-leaning, fast turnarounds. Use for "find X", "summarize Y", "trace dependency chain Z". Do not assign destructive edits to explorers.
- `worker` — code changes. Assign disjoint write ownership when fanning out multiple workers; overlapping write sets cause merge conflicts and duplicated effort.
- Any user-defined agent type from project config is also valid.

Pick the role that matches the work. Don't spawn an explorer to write code; don't spawn a worker to grep.

## Cost

Every spawned agent makes its own LLM calls and consumes context budget. Cost is multiplicative — five concurrent agents is roughly five times the token spend per turn. The depth cap is 4 levels under `/root`; the per-session concurrent thread cap may also reject a spawn (close finished agents to free slots). Spawn deliberately, not reflexively.
