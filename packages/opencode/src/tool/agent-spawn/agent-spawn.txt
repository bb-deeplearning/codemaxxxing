Spawn a sub-agent to run concurrently in its own fiber. Returns immediately
with the child's canonical task name and nickname; the child runs in
parallel while you keep working. The child can spawn its own children, send
you messages via send_message / followup_task, and reach a final status that
you observe via wait_agent or list_agents.

## Mental model

Spawning is asynchronous and non-blocking. The call returns as soon as the
child is registered and its run-loop fiber is forked — usually a few
milliseconds. The child then makes its own LLM calls, runs its own tools,
and may spawn its own children. Treat sibling agents as separate workers,
not as function calls. You and they make progress in parallel.

## Naming and addressing

`task_name` is the leaf of the new agent's canonical path. Lowercase
letters, digits, and underscores only — `worker_1`, `parser_review`, `db`.
If your path is `/root/explorers` and you spawn with `task_name: "worker_a"`,
the child's canonical path is `/root/explorers/worker_a`. From your
perspective you can refer to the child as `worker_a` (relative) or
`/root/explorers/worker_a` (canonical). A sibling at `/root/builders` can
only refer to it by the canonical form. Pick names that mean something —
they show up in `list_agents` and in every cross-agent message.

## Inheritance and model selection

The child inherits your workspace and permission ruleset. When `model` is
unset, resolution walks: the agent type's configured model, else the model
YOU are currently running (nearest ancestor in the spawn chain with a model
pick), else the machine-global default as a last resort.

Agent-type pins are the routing matrix's defaults — for most spawns, leaving `model` unset and picking the right `agent_type` IS the routing decision. Override `model` (as `provider/model`, e.g. `anthropic/claude-opus-4-8`) when the task tier demands it per the routing matrix in your instructions files: judgment work routes to stronger models, mechanical machine-verifiable work routes to cheaper ones. Add `reasoning_effort` to select one
of that model's reasoning variants (e.g. `low`, `high`); it requires
`model` to be set. Both are validated at spawn time — an unknown model or
an invalid variant fails the call (listing valid variants) instead of
silently spawning the child on the wrong model.

`agent_type` selects which subagent definition to spawn — see the
Subagents section below.

## When to delegate

- Bounded sidecar work that can run in parallel with your immediate next
  step. Prefer delegating concrete, well-scoped tasks.
- Multiple independent research questions — fan out N `explore` agents,
  integrate results when they return.
- Code edits with disjoint write sets — split the work, spawn one agent
  per slice, do not let two agents touch the same files.
- Debate / design review — spawn two agents with different framings and
  let them followup_task each other.
- Observer/worker — one agent watches outputs of N siblings via wait_agent
  and integrates the results.

## When NOT to delegate

- Your immediate next blocking step. If you need the answer to make the
  next decision, do it locally — don't hand it off and then sit on
  wait_agent.
- Tightly-coupled work that touches the same files or state another agent
  is already working on.
- Tasks too vague to scope cleanly. A delegated task with unclear output
  produces unclear results. Sharpen the ask first or do it yourself.
- The same question you already delegated. If a previous spawn's answer
  was unsatisfactory, refine the prompt and use followup_task on the
  existing agent instead of spawning a duplicate.

## Scoping a delegated task

Every spawn should have a concrete deliverable. "Look into X" is bad;
"return the file paths and line numbers where Y is implemented, and the
function signatures involved" is good. For code-edit work, name the files
the child owns and forbid edits outside that set. For research work, name
the questions and the format you expect back.

## After you delegate

Do useful local work. Don't reflexively call wait_agent — that just blocks
your fiber while the child is still running. Check in with list_agents
when you need a status snapshot, or wait_agent only when you're genuinely
blocked on a result for your next step. Read drained messages in your
mailbox — siblings push results to you via send_message and they appear at
the start of your next turn.

## Subagents

`agent_type` names which subagent to spawn — pick from the agent types
listed below this description (the registry templates the live list per
turn so it always reflects what's actually available).

Pick the subagent that matches the work. Match the description to the
task; if no listed subagent is a clean fit, do the work locally instead
of forcing one in.

## Cost

Every spawned agent makes its own LLM calls and consumes context budget.
Cost is multiplicative — five concurrent agents is roughly five times the
token spend per turn. Don't spawn for trivia. A grep, a glob, or a quick
read is cheaper than spawning an explorer. Spawn when the work is
substantial enough that running it in parallel actually saves wall-clock
time.

## Limits

- Spawn depth is capped at 4 levels under `/root` — `/root/a/b/c/d` is the
  deepest legal path. A 5th level is rejected with a depth error.
- The session may also impose a max concurrent thread cap. If you exceed
  it the spawn errors — close finished agents with `close_agent` to free
  slots.

## fork_turns

Controls how much of your conversation history the child inherits.
- `"none"` (default): no history. Children are isolated context windows —
  that is the point of spawning. Write a complete brief; attach `files`
  for artifacts.
- `"all"`: full history, copied into the child at spawn. Opt-in, and you
  pay its full token cost on the child's first model call. For agents
  that genuinely need the conversation record (design review, debate).
- A positive integer string (e.g. `"3"`): the most recent N turns, for
  when only recent context matters.

Only completed turns are copied — your in-flight turn (the one making
this spawn call) is excluded, so the child never sees your unfinished
tool calls. Copies are context, not instructions: the child acts on the
initial message, with your history as background.

## files

Attach specific files to the child's first message. Each path (absolute,
or relative to the project root) is read at spawn time and appended as an
`[attached file: ...]` fenced block. This is the middle ground the fork
options lack: `fork_turns: "none"` + `files: [...]` hands a self-contained
child exactly the artifacts it needs — no full-history token cost, no
hand-pasting file contents into the message string. Oversized files are
head/tail-elided with an explicit marker. Unreadable paths fail the spawn
(`files_unreadable`) rather than silently spawning an under-informed child.

## Supervision strategies (D12)

Two optional parameters control how the runtime supervises this child
when its run-loop reaches a terminal status. Both default to today's
implicit behavior — existing call sites need no changes.

`on_failure` declares what happens when the child terminates non-cleanly
(crash, errored status):

- `escalate` (default): the runtime forwards an errored notification to
  your mailbox. You decide what to do next (close, retry, ignore).
- `respawn`: the runtime re-spawns the child at the same task_name with
  a fresh session id, capped at 3 attempts. After the cap, the runtime
  escalates with a respawn-cap-exceeded notification (abort_reason.reason
  = `transient_tool_error`).
- `ignore`: the runtime swallows the failure silently. You receive no
  completion notification. Useful for fire-and-forget probes you do not
  want to react to.
- `kill_pool`: stub-only this release. Wave 6 wires pool teardown
  semantics.

`pool_strategy` declares how a failure in one pool member affects its
siblings (Erlang OTP-style):

- `one_for_one` (default): pool failures are isolated; surviving
  siblings keep running.
- `one_for_all`: any single failure tears down the entire pool. Wired in
  Wave 6.
- `rest_for_one`: any single failure tears down pool members spawned
  after the failing one. Wired in Wave 6.

Today, both params are stored on the per-child slot until Wave 6's
`spawn_pool` wires active behavior.

## isolation

`isolation: "worktree"` gives the child its own git checkout on its own
branch (named from task_name) under the data dir. Its writes land there,
never in your cwd — parallel WRITER fan-out becomes structurally safe
instead of discipline-dependent. The checkout boots alive: tracked files,
.worktreeinclude-declared ignored files (.env, node_modules), instance,
and start scripts are all ready before the child's first turn.

At terminal status the checkout settles itself: clean → removed silently;
commits or dirt → kept, and the completion notification reports branch,
commits ahead, and dirt so you can merge, send back (followup_task), or
discard through the worktree surface. A respawned child continues in the
same checkout.

Defaults: the agent type's configured `isolation`, else `none`. Read-only
children (explore) should never pay for isolation — keep them in the
shared directory.
