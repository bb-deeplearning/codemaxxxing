Spawn a command in a persistent PTY session and return its initial output. `exec_command` keeps the child alive after the call returns, hands you back a `session_id`, and lets you re-enter via `write_stdin` to send more input or poll for new output.

Use this tool for processes that hold state between interactions or run indefinitely:

- REPLs — `python`, `ipython`, `node`, `bun repl`, `psql`, `redis-cli`, `ghci`, `iex`. The interpreter loads its imports, parses your file, builds whatever in-memory state you need; subsequent `write_stdin` calls reuse that state without re-paying the boot cost.
- Dev servers — `next dev`, `vite`, `cargo run`, `bun run dev`. Spawn once, then poll with empty `write_stdin` to read fresh log lines as the server reacts to file edits you make in parallel.
- File watchers — `tsc --watch`, `cargo watch`, `vitest --watch`. Same pattern: spawn once, poll for new diagnostics.
- ssh / docker exec / interactive db shells — anything where the connection setup is expensive and you'll send multiple commands.
- Long-running observables — `tail -f`, `kubectl logs -f`, `journalctl -f`.

For one-shot commands that exit on their own (`ls`, `git status`, `npm install`, scripts), set `yield_time_ms` long enough for the process to exit and the call returns the full output with `exit_code` populated. No persistence overhead is incurred when the process terminates inside the yield window.

IMPORTANT: This tool is for terminal operations like git, npm, docker, etc. DO NOT use it for file operations (reading, writing, editing, searching, finding files) - use the specialized tools for this instead:
- File search: Use Glob (NOT find or ls)
- Content search: Use Grep (NOT grep or rg)
- Read files: Use Read (NOT cat/head/tail)
- Edit files: Use Edit (NOT sed/awk)
- Write files: Use Write (NOT echo >/cat <<EOF)
- Communication: Output text directly (NOT echo/printf)

# Parameters

- `cmd` (required) — the shell command. Treated as a string passed to your default shell; quoting and globbing follow shell rules.
- `workdir` — directory to run in. Defaults to the turn's cwd. Pass an absolute path or a path relative to the turn cwd.
- `shell` — override the shell binary. Defaults to your configured shell. Most use cases shouldn't touch this.
- `tty` (default `false`) — allocate a TTY. **Required if you intend to send stdin later via `write_stdin`.** Without `tty: true`, the connection is one-way: you can poll for output but cannot write input. REPLs need `tty: true`. Dev servers usually do too (some emit colored TTY output). File watchers usually don't.
- `yield_time_ms` (default `10000`) — how long to wait for output before returning. The call returns either when this elapses or when the process exits, whichever first. Clamped to [250, 30000]. For REPL prompts, 1000-3000 is responsive. For dev server cold-start, 5000-10000. For one-shot commands you expect to finish, 30000.
- `max_output_tokens` — cap returned output length. Excess truncates head+tail (you see prologue and tail with the middle elided). Default budget is set by the configured truncation policy; raise this if you specifically need more context.

# Return shape

```
{
  output: string                    // command output, possibly head/tail-truncated
  wall_time_seconds: number         // elapsed wait time
  session_id?: number               // present iff process is still running
  exit_code?: number                // present iff process exited during this call
  chunk_id?: string                 // present iff partial output (still running)
  original_token_count?: number     // approx tokens before truncation
}
```

`session_id` is the discriminator: present means the process is alive and you can call `write_stdin` against it. Absent means the process exited (check `exit_code`). Either field is present per call, never both.

# Operational discipline

- **`session_id` is per-instance and per-spawn.** It does NOT survive `opencode` restart. If you previously had a session and `opencode` was restarted, that `session_id` is gone — re-spawn with a fresh `exec_command`. Same for sessions that hit the LRU cap (64 concurrent processes; oldest non-recent ones get pruned).
- **First spawn requires permission. Subsequent `write_stdin` against the same `session_id` does not.** When you approve "always" for the first `exec_command`, the per-PID pattern `pid:<session_id>` registers as allowed; `write_stdin` finds it and skips the prompt. This holds for the life of the process, not the session_id string.
- **Output is head/tail-truncated, not tail-only.** If the process emits more bytes than `max_output_tokens` allows, you see a prefix (the prologue, often the most informative for "did it start cleanly") and a suffix (the tail, with the most recent activity). The middle is dropped. When interpreting long output, remember the gap is real.
- **Pool cap is 64.** When you spawn the 65th, the LRU pruner kills the oldest non-recent one. The 8 most-recently-used are protected; among the rest, exited entries die first, then alive ones in LRU order. If you run a lot of `exec_command` with quick exit, those exited shells get reaped first — you don't have to manage them.
- **A 60-process warning fires when you cross that threshold.** Treat it as a signal to consolidate or close work, not a hard limit. The 64-cap pruning happens silently.
- **`ctx.abort` (user Cmd-C) terminates the spawned process** and surfaces "User aborted the command" in metadata. Output collected so far still returns.

# Failure modes

- Permission denied → the call returns an error and the spawned process is torn down before output collection.
- Spawn failure (binary not found, cwd doesn't exist) → error message names the cause; no `session_id` returned.
- Process exits during initial yield → `exit_code` returned, no `session_id`. Treat as a one-shot result.
- `cwd` resolves outside the workspace → permission system asks for `external_directory` (separate prompt) before spawning.

# Cost model

Each persistent process holds a slot in the 64-cap pool, a PTY (real OS resource), and a 1 MiB head/tail output buffer. Cheap enough to spawn liberally; expensive enough to not fire-and-forget thousands. If you spawned a process speculatively and don't need its output anymore, there's no explicit close — the LRU pruner reclaims it once you've spawned enough other things, or it dies with the project instance.

# Committing changes with git

Only create commits when requested by the user. If unclear, ask first. When the user asks you to create a new git commit, follow these steps carefully:

Git Safety Protocol:
- NEVER update the git config
- NEVER run destructive/irreversible git commands (like push --force, hard reset, etc) unless the user explicitly requests them
- NEVER skip hooks (--no-verify, --no-gpg-sign, etc) unless the user explicitly requests it
- NEVER run force push to main/master, warn the user if they request it
- Avoid git commit --amend. ONLY use --amend when ALL conditions are met:
  (1) User explicitly requested amend, OR the commit succeeded and pre-commit hooks auto-modified files that need including — verify by checking `git log` that HEAD is the new commit before amending
  (2) HEAD commit was created by you in this conversation (verify: git log -1 --format='%an %ae')
  (3) Commit has NOT been pushed to remote (verify: git status shows "Your branch is ahead")
- CRITICAL: If commit FAILED or was REJECTED by hook, NEVER amend - fix the issue and create a NEW commit
- CRITICAL: If you already pushed to remote, NEVER amend unless user explicitly requests it (requires force push)
- NEVER commit changes unless the user explicitly asks you to. It is VERY IMPORTANT to only commit when explicitly asked, otherwise the user will feel that you are being too proactive.

1. You can call multiple tools in a single response. When multiple independent pieces of information are requested and all commands are likely to succeed, run multiple tool calls in parallel for optimal performance. run the following commands in parallel, each using the exec_command tool:
  - Run a git status command to see all untracked files.
  - Run a git diff command to see both staged and unstaged changes that will be committed.
  - Run a git log command to see recent commit messages, so that you can follow this repository's commit message style.
2. Analyze all staged changes (both previously staged and newly added) and draft a commit message:
  - Summarize the nature of the changes (eg. new feature, enhancement to an existing feature, bug fix, refactoring, test, docs, etc.). Ensure the message accurately reflects the changes and their purpose (i.e. "add" means a wholly new feature, "update" means an enhancement to an existing feature, "fix" means a bug fix, etc.).
  - Do not commit files that likely contain secrets (.env, credentials.json, etc.). Warn the user if they specifically request to commit those files
  - Draft a concise (1-2 sentences) commit message that focuses on the "why" rather than the "what"
  - Ensure it accurately reflects the changes and their purpose
3. You can call multiple tools in a single response. When multiple independent pieces of information are requested and all commands are likely to succeed, run multiple tool calls in parallel for optimal performance. run the following commands:
   - Add relevant untracked files to the staging area.
   - Create the commit with a message
   - Run git status after the commit completes to verify success.
   Note: git status depends on the commit completing, so run it sequentially after the commit.
4. If the commit fails due to pre-commit hook, fix the issue and create a NEW commit (see amend rules above)

Important notes:
- NEVER run additional commands to read or explore code, besides git commands
- NEVER use the TodoWrite or Task tools
- DO NOT push to the remote repository unless the user explicitly asks you to do so
- IMPORTANT: Never use git commands with the -i flag (like git rebase -i or git add -i) since they require interactive input which is not supported.
- If there are no changes to commit (i.e., no untracked files and no modifications), do not create an empty commit

# Creating pull requests
Use the gh command via the exec_command tool for ALL GitHub-related tasks including working with issues, pull requests, checks, and releases. If given a GitHub URL use the gh command to get the information needed.

IMPORTANT: When the user asks you to create a pull request, follow these steps carefully:

1. You can call multiple tools in a single response. When multiple independent pieces of information are requested and all commands are likely to succeed, run multiple tool calls in parallel for optimal performance. run the following commands in parallel using the exec_command tool, in order to understand the current state of the branch since it diverged from the main branch:
   - Run a git status command to see all untracked files
   - Run a git diff command to see both staged and unstaged changes that will be committed
   - Check if the current branch tracks a remote branch and is up to date with the remote, so you know if you need to push to the remote
   - Run a git log command and `git diff [base-branch]...HEAD` to understand the full commit history for the current branch (from the time it diverged from the base branch)
2. Analyze all changes that will be included in the pull request, making sure to look at all relevant commits (NOT just the latest commit, but ALL commits that will be included in the pull request!!!), and draft a pull request summary
3. You can call multiple tools in a single response. When multiple independent pieces of information are requested and all commands are likely to succeed, run multiple tool calls in parallel for optimal performance. run the following commands in parallel:
   - Create new branch if needed
   - Push to remote with -u flag if needed
   - Create PR using gh pr create with the format below. Use a HEREDOC to pass the body to ensure correct formatting.
<example>
gh pr create --title "the pr title" --body "$(cat <<'EOF'
## Summary
<1-3 bullet points>
</example>

Important:
- DO NOT use the TodoWrite or Task tools
- Return the PR URL when you're done, so the user can see it
