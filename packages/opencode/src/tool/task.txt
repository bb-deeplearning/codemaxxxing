Launch a new agent to handle complex, multistep tasks autonomously.

Available agent types and the tools they have access to:
{agents}

When using the Task tool, you must specify a subagent_type parameter to select which agent type to use. Always include a short description (3-5 words) summarizing what the agent will do.

Each subagent invocation has overhead: fresh context window, prompt tokens, latency. Delegate when the work benefits from isolated context, parallel execution, or requires searching across many files. Don't delegate when a direct tool call would be faster.

When to use the Task tool:
- Broad codebase exploration: understanding architecture, finding patterns across many files, answering "how does X work" questions
- Multi-step tasks that benefit from isolated context: self-contained implementation subtasks, complex refactors
- Parallel work: multiple independent research or implementation tasks that can run simultaneously in a single message
- Custom slash commands: Use the Task tool with the slash command invocation as the entire prompt. For example: Task(description="Check the file", prompt="/check-file path/to/file.py")

When NOT to use the Task tool:
- If you want to read a specific file path, use the Read or Glob tool instead
- If you are searching for a specific class definition like "class Foo", use the Glob tool instead
- If you are searching for code within a specific file or set of 2-3 files, use the Read tool instead
- If a single Grep or Glob call would answer the question
- Other tasks that are not related to the agent descriptions above

# Context isolation

Each agent invocation starts with a COMPLETELY fresh context — no conversation history, no prior tool results. The prompt you provide is the ONLY information the agent has.

When starting fresh, your prompt MUST be self-contained. Include:
- The specific task to perform
- All relevant file paths (absolute paths)
- Relevant code snippets if the agent needs to understand current state
- Expected response format and what information to return
- Whether to write code or just do research (the agent does not know the user's intent)

Bad: "Investigate the auth issue we discussed"
Good: "Search the codebase for authentication/authorization logic. Start with src/auth/ and src/middleware/. Look for JWT handling, session management, and permission checks. Return: file paths with line numbers, key function signatures, and how auth flows through the request lifecycle. This is research only — do not modify any files."

To continue a previous agent's session, pass its task_id — this preserves the full context from prior work.

# Usage notes
1. When you have multiple independent tasks, launch agents concurrently in a single message with multiple tool calls. This reduces wall-clock time significantly. If the user specifies "in parallel", you MUST send a single message with multiple Task tool calls.
2. The result returned by the agent is not visible to the user. To show the user the result, send a text message with a concise summary. The output includes a task_id you can reuse to continue the same session.
3. The agent's outputs should generally be trusted.
4. Clearly tell the agent whether you expect it to write code or just research, since it is not aware of the user's intent. Tell it how to verify its work if possible (e.g., relevant test commands).
5. If the agent description mentions proactive use, use it without waiting for the user to ask.
